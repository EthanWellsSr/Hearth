# v0.4.1 Calendar Rhythm — design specification

**Status:** Confirmed 2026-09-18. Recurring Events, the Week view, Chores on the
Calendar, and Household-timezone maintenance shipped in v0.4.1. The Event
reminders and browser-push scope recorded here was split into v0.4.2; this
document remains its authoritative design.

## Design outcome

Make the Household Calendar useful as a weekly rhythm: Members can see repeating
Events and due Chores and work in a seven-day time grid. Chore scheduling and
completed To-do cleanup follow each Household's timezone. The follow-on v0.4.2
release adds the timely Event reminders from this design.

## Confirmed decisions

### Recurring Events

- Recurrence uses a deliberately limited, RFC 5545-compatible rule set: daily,
  weekly, monthly, and yearly frequencies; configurable intervals; multiple
  weekdays for weekly rules; and never, date, or count end conditions.
- Hearth stores a series master plus occurrence exceptions. It expands occurrences
  only for the requested Calendar window and never materializes an unbounded series.
- Members may change or delete one occurrence, this and future occurrences, or the
  entire series. This-and-future changes split the series transactionally.
- A moved occurrence keeps the identity of its original scheduled occurrence.
- Each series records a recurrence timezone copied from the Household timezone at
  creation. A later Household-timezone change does not reinterpret that series.
- Recurring timed Events retain their local wall-clock start in the series timezone.
  Nonexistent spring-forward occurrences are skipped. Repeated fall-back times use
  the first occurrence. Timed one-off Events remain fixed absolute instants.
- Series and occurrence mutations use optimistic concurrency. Occurrence identity
  and exception changes are committed atomically.

### Calendar projection and queries

- Calendar renderers consume a shared occurrence-oriented projection rather than
  treating every rendered item as a stored Event row.
- A Calendar Item identifies its Event or Chore source, stable occurrence key,
  Household-local date range, optional absolute times, presentation data, and
  destination or action.
- Events and Chores remain separate domain entities. Chores are not copied into the
  Events table.
- Calendar data is queried and expanded for explicit date ranges. Month, Upcoming,
  and Week views do not load the Household's complete Event history.

### Seven-day view

- Week means Sunday through Saturday. Upcoming remains a rolling seven-day view.
- The Week view has an all-day lane and a time grid. Overlapping timed Events render
  beside one another.
- Phones retain a real seven-day grid through horizontal scrolling, sticky day
  headers, and a sticky time gutter, initially positioned at today.
- The Upcoming sidebar remains beside the Week view only at sufficiently wide
  desktop widths. The grid otherwise uses the full width.
- Selecting an empty time slot prefills a new Event's date and time. Dragging,
  resizing, and drag-to-create are deferred.
- A timed Event without an end uses a minimum-height start marker and does not imply
  an invented end.

### Chores on Calendar

- Calendar shows only each Chore's stored `next_due` date; it does not predict
  future Chore occurrences.
- Chores appear as all-day Calendar Items. Overdue Chores remain on their actual
  dates and also appear in an explicit Upcoming overdue section.
- Calendar offers a deliberate Complete action and a separate route to Chores.
  Chore changes revalidate both Chores and Calendar.
- Chore date calculations use the Household-local current date. Stored due dates
  remain calendar dates and are never timezone-shifted.

### Completed To-do cleanup

- To-dos record when they become completed.
- Cleanup evaluates every Household in its own timezone during an early-morning
  run and removes completed To-dos from before the current Household-local day.
- Reopening a To-do clears its completion timestamp.

### Event reminders and browser push (v0.4.2)

- v0.4.2 delivers browser push notifications. The in-app notification inbox and
  read state remain part of v0.8.0.
- Notification permission is requested only from an explicit Member action and is
  stored per browser/device. Denial never blocks Calendar use.
- All currently opted-in Household Members receive Event reminders. Selectable
  recipients wait for the attendee model in v0.4.4.
- An Event may have no reminders or multiple offsets. A recurring series owns its
  default reminders; an occurrence exception may override them.
- All-day reminder delivery uses 9:00 AM in the Event or series timezone. Household
  timezone changes reschedule one-off all-day reminders but do not change a series'
  recorded timezone.
- Push payloads contain the Event title and time but never Event details.
- Push subscriptions belong to a User and device endpoint, not a Membership.
- A durable delivery record keyed by reminder, occurrence, recipient, and channel
  makes retries idempotent. Delivery rechecks current Event, Membership, and
  subscription state immediately before sending.
- Supabase Cron is the clock. It invokes a protected sender using deployment-held
  secrets. Delivery is best-effort and does not promise alarm-grade timing.

## Implementation sequence

1. Shared Calendar Item projection and bounded date-range loading.
2. Household-timezone cleanup and Calendar-visible Chores.
3. Seven-day time grid.
4. Recurring Event schema, expansion, and editing flows.
5. PWA manifest hardening.
6. v0.4.2: service-worker support and push subscriptions.
7. v0.4.2: reminder persistence, scheduler, delivery, and retry protection.
8. Full automated, responsive, DST, RLS, and notification verification for each
   release's scope.

## Required acceptance checks

### v0.4.1

- Month, Upcoming, and Week use bounded ranges and render one-off and recurring
  Events consistently.
- Daily, multi-weekday weekly, monthly, and yearly rules honor intervals and all
  three end conditions.
- One-occurrence, this-and-future, and entire-series changes preserve stable
  occurrence identity and reject stale concurrent writes.
- DST gaps are skipped and repeated times choose the first occurrence.
- The Week view handles overlap, all-day and multi-day items, no-end Events, and
  phone horizontal scrolling.
- Chores appear only on `next_due`, overdue Chores remain visible, and completion
  refreshes both Calendar and Chores.
- Chore scheduling and completed To-do cleanup use distinct Household timezones.
- RLS continues to isolate Calendar and recurrence data.

### v0.4.2

- Push opt-in, denial, revocation, multiple devices, changed/deleted Events,
  retries, and removed Members behave safely.
- RLS continues to isolate reminder and subscription data.

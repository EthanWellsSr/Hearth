# v0.4.3 — Production Foundations

Design gate run 2026-09-27 from
[`docs/audits/2026-09-24-public-launch-readiness.md`](../audits/2026-09-24-public-launch-readiness.md).
The audit's scope was split: this release is the infrastructure work that does not
need a domain; sign-up for people outside the Wells Household follows in
[v0.4.4](v0.4.4-public-sign-up.md).

## Goal

Make Hearth's database reproducible, recoverable, and efficient as Households are
added, before any stranger can sign up. Nothing in this release changes what a
Member sees.

## Audience

Hearth will be open for sign-up but not advertised, and stays free (Vercel Hobby
is non-commercial).

## User flows

No new Member-facing flows. One changed behavior:

- A User who already has a Membership and tries to create or join a Household gets
  a clear refusal, enforced by the database rather than only by a function check.

Operator flows (Ethan):

### Change the schema

1. Write a migration in `web/supabase/migrations/`.
2. CI rebuilds a throwaway database from every migration; a broken migration fails
   the PR.
3. Apply to staging with the Supabase CLI and verify.
4. Apply to production with `supabase db push` from Ethan's machine, following the
   release checklist. Production is never changed from the SQL Editor.

### Recover from a bad change

1. Migrations are forward-only: a mistake is fixed by a new migration.
2. Data loss is recovered from the nightly encrypted dump, restored first into
   staging to confirm contents.

## Architecture

### Migrations and environments

- Supabase CLI with a committed `supabase/config.toml`.
- `0001`–`0014` are squashed into one baseline generated from production's current
  schema. The old files move to `web/supabase/archive/`, outside the directory the
  CLI applies; production records the baseline as already applied. The baseline
  contains no Household data (the `'Wells'` seed in `0001` does not carry over).
- A second free Supabase project is **staging**. Vercel Preview deployments and
  local `.env.local` point at staging; the latency harness keeps measuring
  production.
- Staging is populated from a seed file: one neutral fictional Household with two
  Members and sample Chores, Events, and To-dos, plus a bulk seed for index
  evidence. Production data is never copied to staging.
- A new CI job, `migrations`, starts a throwaway Supabase, applies all migrations
  and the seed from scratch, and checks the hand-carried platform objects exist.
- The CLI's schema dump skips platform schemas, so the baseline carries the
  pg_cron job and the avatars Storage bucket and policies by hand;
  `web/scripts/db-dump-schema.sh` snapshots both parts for comparing databases.
- The CLI is linked to staging, so an unqualified command never touches
  production; production commands name it explicitly with `--project-ref`, authenticated by
  the CLI login token rather than the database password.

### Tenant filters

- Every query on a Household-scoped table filters by `household_id` explicitly.
  RLS remains the security guarantee; the filter is the performance path.
- A test fails when a Household-scoped query omits the filter, so new features
  cannot regress it.

### Backups

- A scheduled GitHub Action in a separate **private** repository runs nightly
  `pg_dump` of the `public` and `auth` schemas, encrypts it with `age`, and stores
  it as an artifact kept 30 days. The decryption key lives outside GitHub.
- The job connects with a dedicated read-only role if one can read `auth` on
  Supabase; otherwise it uses the `postgres` password and the reason is recorded.
- Avatar images in Storage are not backed up; Members re-upload after a disaster.
- The nightly job also keeps the Free-tier production project from pausing.

### Security headers and error tracking

- Enforced: `frame-ancestors` / `X-Frame-Options`, `Referrer-Policy`,
  `X-Content-Type-Options: nosniff`, `Permissions-Policy`. Content-Security-Policy
  ships in report-only mode.
- Sentry on server and client: errors only, no tracing, no session replay, User ID
  only (no names or emails), source maps uploaded from Vercel builds.

## Data model

- `(household_id, created_at)` indexes on `todos` and `grocery_items`.
- `unique (user_id)` on `memberships`: one Household per User, enforced by the
  database. The migration first checks for existing duplicates and fails loudly
  instead of deleting rows. `create_household_with_owner` and
  `join_household_with_invite` translate the violation into a clear message.
  Dropping the constraint later re-enables multiple Households (ADR 0001).

## Boundaries

- No domain, custom SMTP, auth routes, CAPTCHA, privacy policy, account deletion,
  or public repository — all v0.4.4.
- No automated production migrations; revisit after branch protection exists.
- No Storage backups, no Supabase Pro.
- Content-Security-Policy is not enforced.

## Repository hygiene

MIT `LICENSE`, a setup README for public readers, neutral names in test fixtures,
empty `debug-performance` directories removed, and future commits authored with
GitHub's noreply address (history is not rewritten).

## Acceptance criteria

- A fresh Supabase database built only from the repository's migrations matches
  production's schema; the CI rebuild job passes.
- Production's migration history shows the baseline and every later migration,
  applied by the CLI.
- Staging exists, holds only seeded data, and Vercel Previews use it.
- Every Household-scoped query filters by `household_id`, and the guard test fails
  when one is removed.
- `EXPLAIN` on staging's bulk seed shows the To-do and Grocery List queries using
  the new indexes.
- Creating or joining a second Household is refused by the database, including two
  concurrent attempts.
- A nightly backup has run, and one dump has been decrypted and restored into
  staging.
- Response headers show the enforced set and a report-only CSP.
- A deliberate server error and client error both appear in Sentry with readable
  stack traces and no personal data.
- `npm run lint`, `npm test`, `npm run build -- --webpack`, and
  `npm run notices:check` pass.

## Delivery sequence

1. Supabase CLI, `config.toml`, baseline migration, staging project, CI rebuild job.
2. Tenant filters, indexes, and the unique Membership, as the first migrations
   through the new process.
3. Backups and a test restore.
4. Security headers, Sentry, and repository hygiene.

## Goal

Make Hearth's database schema reproducible and Household queries efficient.
The migrations and seed recreate an empty application with fictional sample
data; they do not restore production Household records. Nothing in this release
changes what a Member sees.

## Audience

No new sign-up audience is introduced in v0.4.3. Public sign-up is a separate
release decision. Existing Members can sign in; Invite Codes cannot create new
Auth Users while registration is disabled.

## User flows

No new Member-facing flows. One changed behavior:

- A User who already has a Membership and tries to create or join a Household gets
  a clear refusal, enforced by the database rather than only by a function check.

Operator flows (Ethan):

### Change the schema

1. Write a migration in `web/supabase/migrations/`.
2. CI rebuilds a throwaway database from every migration; a broken migration fails
   the PR.
3. Apply to staging with the Supabase CLI and verify.
4. Apply to production with `supabase db push` from Ethan's machine, following the
   release checklist. Production is never changed from the SQL Editor.

### Recover from a bad change

Migrations are forward-only: a schema mistake is fixed by a new migration.
Recovering deleted production Household records requires the later backup and
restore process; migrations alone cannot do that.

## Architecture

### Migrations and environments

- Supabase CLI with a committed `supabase/config.toml`.
- `0001`–`0014` are squashed into one baseline generated from production's current
  schema. The old files move to `web/supabase/archive/`, outside the directory the
  CLI applies; production records the baseline as already applied. The baseline
  contains no Household data (the `'Wells'` seed in `0001` does not carry over).
- A second free Supabase project is **staging**. Vercel Preview deployments and
  local `.env.local` point at staging; the latency harness keeps measuring
  production.
- Staging is populated from a seed file: one neutral fictional Household with two
  Members and sample Chores, Events, and To-dos, plus a bulk seed for index
  evidence. Production data is never copied to staging.
- A new CI job, `migrations`, starts a throwaway Supabase, applies all migrations
  and the seed from scratch, and checks the hand-carried platform objects exist.
- The CLI's schema dump skips platform schemas, so the baseline carries the
  pg_cron job and the avatars Storage bucket and policies by hand;
  `web/scripts/db-dump-schema.sh` snapshots both parts for comparing databases.
- The CLI is linked to staging, so an unqualified command never touches
  production; production commands name it explicitly with `--project-ref`, authenticated by
  the CLI login token rather than the database password.

### Tenant filters

- Every query on a Household-scoped table filters by `household_id` explicitly.
  RLS remains the security guarantee; the filter is the performance path.
- A test fails when a Household-scoped query omits the filter, so new features
  cannot regress it.

### Backups (deferred until after repository publication)

- A scheduled GitHub Action in a separate **private** repository runs nightly
  `pg_dump` of the `public` and `auth` schemas, encrypts it with `age`, and stores
  it as a private workflow artifact. The decryption key lives outside GitHub.
- Set artifact retention after measuring dump size against GitHub Free storage;
  aim for 30 days while within the free allowance. Alert on missed or failed
  runs, and verify a restore into an isolated non-production database.
- The job connects with a dedicated read-only role if one can read `auth` on
  Supabase; otherwise it uses the `postgres` password and the reason is recorded.
- Avatar images in Storage are not backed up; Members re-upload after a disaster.

### Security headers and error tracking (original proposal; deferred)

- Enforced: `frame-ancestors` / `X-Frame-Options`, `Referrer-Policy`,
  `X-Content-Type-Options: nosniff`, `Permissions-Policy`. Content-Security-Policy
  ships in report-only mode.
- Sentry on server and client: errors only, no tracing, no session replay, User ID
  only (no names or emails), source maps uploaded from Vercel builds.

### Scale test

Proves Hearth holds a small public launch before sign-up opens (added 2026-09-29).
Runs against staging only; staging and production are both on Supabase's free
tier, so staging results stand in for production.

- **Target:** 1,000 Households, 2,000 Users (two Members each), 50 Users active at
  once. A short ramp to 100 records headroom but does not gate.
- **Data:** a scale seed, separate from the CI seed and applied to staging only:
  per Household 2 Members, 100 To-dos, 100 Grocery Items, 4 Events, 4 Chores.
  One bcrypt hash is reused for every scale User so seeding stays fast.
- **Database layer (primary):** `pgbench` sessions act as signed-in Users —
  `set role authenticated` plus the request JWT claims — so RLS and `auth.uid()`
  run exactly as they do through PostgREST. Each virtual User loops the real page
  reads (shell context, Home, To-dos, Groceries, Chores, Calendar window) and
  common writes (toggle To-do, add Grocery Item, create Event) with think time.
  Run by Claude with the CLI's temporary login role; no password needed.
- **End to end (optional):** `k6` drives a Preview deployment through Vercel
  Functions, Auth, and the database with a small User sample. It needs a Vercel
  Protection Bypass for Automation secret and signs in with the scale test
  password, so Ethan runs it; Claude writes the script. It consumes Hobby
  Function allowance, so it stays short.
- **Measured:** per-page and per-query latency (p50/p95), error count, database
  CPU and connections, and `pg_stat_statements` for the slowest queries.
- **Database pass:** at 50 active Users, zero errors, page database work p95
  < 250 ms, database CPU < 70%. The Preview `k6` result is not a release gate.
- **Timing:** one run before delivery step 2 (baseline) and one after it, so the
  tenant filters and indexes show their effect in numbers.
- **Harness:** `web/supabase/seeds/scale.sql` and `web/scripts/scale/run.sh`
  (results in `web/scripts/scale/results/`, not committed).

**Baseline, 2026-09-29 (before step 2): FAIL.** 50 Users (10 pages/s) for 120 s.
Only 367 of about 1,200 page loads completed; the queue reached 89 s. To-dos and
Grocery List pages took about 7.5 s of database time at p50 (1.5 s with no
load), because RLS runs `is_member()` on all 100,000 rows before returning a
Household's 100. Home, Calendar, and writes stayed at 200–370 ms p95 but waited
behind them. No errors in the harness, but the app's `authenticated` role has an
8 s `statement_timeout`, so through PostgREST many of those requests would have
failed.

**After step 2, 2026-09-29: PASS.** Migrations `20260929120000_tenant_scale`
(policies compare `household_id` against `my_household_ids()`, the two list
indexes plus `memberships(household_id)`, unique Membership per User) and
`20260929130000_profile_policy_scale` (profile policy via
`my_household_user_ids()`; `get_my_household_context()` uses `(select
auth.uid())` so it can use the primary key under RLS), with explicit
`household_id` filters in the app.

| Run | Pages done | Errors | DB time per page | Slowest statement | Busy |
|---|---|---|---|---|---|
| Baseline, 50 Users | 367 of ~1,200 | 0 (timeouts in the app) | ~2.8 s | 8.5 s | 8.5 queries at once |
| After, 50 Users | 1,198 of ~1,200 | 0 | 3 ms | 33 ms | 0.03 |
| After, 100 Users | 2,342 of ~2,400 | 0 | 2.8 ms | 17 ms | 0.05 |

The first migration alone left `get_my_household_context()` at ~55 ms and 97%
of database time; the profile-policy fix took it to ~1.4 ms. A To-do query that
omits the filter now costs ~32 ms (a scan with one Household lookup) instead of
1.5 s. The harness runs from a laptop ~80 ms from staging, so client-side page
times are dominated by round trips; server-side times from
`pg_stat_statements` are the database measure. The optional end-to-end `k6` run
remains unperformed.

## Data model

- `(household_id, created_at)` indexes on `todos` and `grocery_items`.
- `unique (user_id)` on `memberships`: one Household per User, enforced by the
  database. The migration first checks for existing duplicates and fails loudly
  instead of deleting rows. `create_household_with_owner` and
  `join_household_with_invite` translate the violation into a clear message.
  Dropping the constraint later re-enables multiple Households (ADR 0001).

## Boundaries

- No domain, custom SMTP, auth routes, CAPTCHA, privacy policy, or account
  deletion — those remain part of the separate public sign-up plan. Repository
  visibility is decided separately.
- No automated production migrations; revisit after branch protection exists.
- Production-data backup and restore are planned for v0.4.4 after repository
  publication. Storage objects are outside the proposed database backup until
  their backup need is decided.
- No new Content-Security-Policy, security headers, or error tracker.

## Repository hygiene

The original proposal was an MIT `LICENSE`, a setup README for public readers,
neutral names in test fixtures, removal of empty `debug-performance` directories,
and future commits from GitHub's noreply address. These are not v0.4.3 gates;
repository-publication choices are separate.

## Acceptance criteria

- A fresh Supabase database built only from the repository's migrations matches
  production's schema; the CI rebuild job passes.
- Production's migration history shows the baseline and every later migration,
  applied by the CLI.
- Staging exists, holds only seeded data, and Vercel Previews use it.
- Every Household-scoped query filters by `household_id`, and the guard test fails
  when one is removed.
- `EXPLAIN` on staging's bulk seed shows the To-do and Grocery List queries using
  the new indexes.
- Creating or joining a second Household is refused by the database, including two
  concurrent attempts.
- The scale test passes at 50 active Users on staging's 1,000-Household scale
  seed, with before/after-step-2 results recorded.
- `npm run lint`, `npm test`, `npm run build -- --webpack`, and
  `npm run notices:check` pass.

## Delivery sequence

1. Supabase CLI, `config.toml`, baseline migration, staging project, CI rebuild job.
2. Scale seed and baseline scale run; then tenant filters, indexes, and the
   unique Membership, as the first migrations through the new process; then the
   scale run again.
3. Complete release checks and hand off the public repository work. Backups
   follow repository publication as a separate task.

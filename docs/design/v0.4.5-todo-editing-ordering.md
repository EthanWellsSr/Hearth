# v0.4.5 — To-do Editing & Ordering

## Confirmed design

Ethan confirmed these decisions in conversation on 2026-10-21 and authorized
implementation, including recording this design without the unavailable
`grill-with-docs` skill.

- Either Member can edit any To-do's text, optional due date, and Assignee.
- One Household list has one persisted order, independent of assignment.
- Drag handles and move-up/down buttons both support reordering.
- Completed To-dos appear below unfinished To-dos.
- New To-dos appear at the bottom of the unfinished list.

## Flows and boundaries

Add a To-do with text, optional date, and optional Assignee. Edit these fields
in an inline form with Save and Cancel. Errors preserve entered values.
Completion moves a To-do into the completed section; reopening restores its
saved relative position among unfinished To-dos. Move controls operate within
completion sections. Dragging starts only on a handle, preserving phone scrolling
elsewhere; buttons provide a keyboard and touch alternative. No personal/shared
list split, recurrence, reminders, filters, or authentication changes.

## Data and request flow

Add nullable `due_date date` and indexed `sort_order bigint` to `todos`.
Dates are calendar dates with no timezone conversion. A sequence gives new rows
a position after existing rows. Backfill preserves creation order with ID ties.
The page reads unfinished first, then saved position and ID.

Screen → authenticated server action → user-scoped database client → refresh.
Edits update all three fields together, scoped by Household; existing RLS and
Assignee validation remain active. A security-invoker reorder function accepts a
moved row and neighboring target rather than a stale client list. It serializes
Household reorders, locks current rows, checks matching completion states, then
updates positions in one transaction. Concurrent edits touch separate columns;
concurrent moves apply sequentially to the latest order. Concurrent additions
remain at the end. No service-role client is used.

## Acceptance criteria

- Either Member can edit and clear date/Assignee without recreating the row.
- Invalid dates, blank text, and invalid Assignees fail without partial writes.
- Order survives refresh and is shared by Members; completion and new-item
  placement follow the confirmed rules.
- Buttons disable at section boundaries; drag works with pointer input.
- Failed saves show an error and preserve the current screen for retry.
- Cross-Household edits/moves and cross-section moves are rejected.
- Verify action behavior, ordering/concurrency/RLS, lint, tests, build, and
  desktop/phone UI where the environment permits.

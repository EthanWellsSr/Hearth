# v0.4.2 — Responsive Application Architecture

## Goal

Make Hearth respond immediately to ordinary authenticated interactions and reduce
the actual time spent waiting on server-rendered navigation. Product complexity
must not translate into a blank or apparently unresponsive interface.

## User flows

### Navigate between Hearth spaces

1. A Member selects Calendar, To-dos, Grocery List, Chores, People, or Profile.
2. The existing authenticated shell remains visible and interactive.
3. Hearth acknowledges the navigation within 100ms with the prefetched route or a
   loading state.
4. The destination replaces the loading state when its authorized data arrives.

### Change a Calendar view

1. A Member selects Upcoming, Month, or Week.
2. Hearth responds immediately without rebuilding the shared header.
3. One bounded database request loads the Event, Event Occurrence exception, and
   Chore rows needed for the requested window.
4. TypeScript expands recurring Events and renders Calendar Items as it does now.

### Mutate existing data

1. Reversible controls such as completion and assignment acknowledge the action
   immediately and expose a saving state.
2. Destructive or compound Event operations remain server-confirmed and disable
   repeated submission while pending.
3. A failed mutation restores the previous visible state and presents its existing
   error path; authorization and concurrency failures are never hidden.

## Architecture

### Runtime placement

- Vercel Functions run in Portland (`pdx1`), near the Supabase primary in Oregon.
- Region selection is committed in `web/vercel.json` so deployment placement is
  reviewable and reproducible.

### Persistent authenticated shell

- Authenticated routes share one route-group layout.
- The layout owns `AppHeader`; pages own only their page-specific content.
- A route-group `loading.tsx` provides immediate, interruptible navigation while a
  dynamic Server Component renders.
- Login, Invitation Link, User Profile setup, and onboarding flows remain outside
  the authenticated layout because they do not yet have a complete Household
  context.

### Request context module

- `requireHousehold()` remains the application interface for authenticated,
  Household-scoped work.
- Its implementation calls one RLS-active database function that returns the User
  Profile, Membership, and Household timezone together.
- `requireProfile()` remains available for pre-Membership setup flows.
- JWT claims are still verified before trusting the User identity. Server Actions
  and protected pages continue to authorize every request; the persistent layout
  is a presentation optimization, not an authorization decision.

### Calendar window module

- `loadCalendarItems()` remains the interface used by Calendar pages.
- Its database adapter calls one RLS-active function for the bounded window rather
  than composing eleven PostgREST requests plus an exception request.
- The function returns source rows as JSON: Events, Chores, and Event Occurrence
  exceptions. Recurrence expansion, timezone behavior, and Calendar Item
  projection stay in TypeScript.
- The migration adds functions only. It does not change Hearth's domain tables or
  tenancy model.

### Avatar URLs

- Private Avatars remain private.
- Signed Avatar URLs are cached server-side by storage path for less than their
  one-hour validity and invalidated when a User Profile changes.
- Ordinary navigation reuses the authenticated layout instead of signing the same
  Avatar again.

### Client state

- Hearth remains Server Component-first for initial reads, authorization, and
  mutations.
- Client memory may provide immediate pending or optimistic state during the
  current session.
- Household data is not persisted to local storage.
- Server revalidation remains authoritative after every mutation.

## Data model

No domain entities or relationships change. Migration `0012` adds two
`SECURITY INVOKER` functions that preserve RLS:

- `get_my_household_context()` returns the current User Profile plus optional
  Membership and Household context.
- `get_calendar_window(...)` returns the authorized source rows needed for a
  bounded Calendar window.

Neither function accepts or returns secret credentials. Household isolation
continues to be enforced by existing table policies.

## Boundaries

Included:

- Region alignment, authenticated layout, loading state, Avatar URL reuse,
  consolidated Household context, consolidated Calendar reads, and immediate
  feedback for existing high-frequency controls.
- Automated tests for request deduplication, returned database payload handling,
  loading/pending behavior where practical, and all existing Calendar behavior.

Excluded:

- Event Reminders and browser push, now v0.4.4.
- A full single-page-application rewrite or persistent offline data cache.
- Public Avatars, weakened JWT validation, bypassed RLS, or client-held service
  credentials.
- New domain entities or changes to recurrence semantics.

## Acceptance criteria

- Visible navigation response within 100ms through a prefetched route or loading
  state.
- Across 20 normal warm production transitions, median destination readiness is
  at most 500ms and p95 is at most 1,000ms.
- A cold authenticated navigation is at most 1.5s under normal service health.
- Ordinary navigation does not request a new signed URL for the current Avatar.
- Calendar source data uses one database round trip per bounded window.
- Authentication, RLS, Household isolation, recurrence, and optimistic concurrency
  remain unchanged.
- Lint, TypeScript, tests, webpack build, notices check, desktop verification, and
  phone-width verification pass before release.

## Delivery sequence

1. Record the release and performance measurement harness.
2. Align Vercel Functions with the database region.
3. Add the persistent authenticated shell and loading state.
4. Cache Avatar signing and invalidate it on profile changes.
5. Add migration `0012` and switch request context and Calendar loading to its
   functions.
6. Add pending/optimistic interaction feedback.
7. Measure locally, apply the migration only with explicit authorization, deploy
   only with explicit authorization, then repeat production measurements.
